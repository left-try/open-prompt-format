# RFC: воспроизводимые версии промптов

Статус: идея реализована экспериментально. Точный контракт локального реестра и релизов описан в [спецификации](../spec/REGISTRY.md); исходный RFC — в [документе реестра](registry-rfc.md). `opf/0.1` описан [отдельно](../spec/SYNTAX.md).

## Зачем нужна отдельная версия

Git хранит историю правок, но приложение должно уметь выбрать именованный релиз и проверить весь набор файлов, который использовался при рендере. Поэтому предлагается различать:

- **Правку:** любой Git-коммит или незакоммиченное изменение.
- **Релиз:** аннотированный тег `opf/<id>/v<semver>` на коммите плюс `bundle_digest` всех исходников и значимых параметров рендера.
- **Канал:** указатель на версию и digest в едином `opf.yaml`; изменение указателя видно в Git.
- **Вызов:** квитанцию с релизом, `bundle_digest`, `render_digest` и фактическими настройками модели.

Номер версии не обязан меняться при каждом редактировании. Команда `release` отказывает, если имя версии уже существует. Проверка digest обнаруживает изменение содержимого или передвижение тега. Один `source_digest` файла из v0.1 не охватывает Jinja-зависимости, поэтому для релиза нужен digest всего набора.

Модель и провайдер не входят в идентичность релиза промпта. Если тот же релиз вызывается на другой модели, квитанция фиксирует другую модель, но релиз промпта не меняется. Необязательные результаты eval могут связывать релиз с испытанными моделями.

`opf/0.1` требует `version` в каждом Markdown-файле. Реализованный `opf/0.2` убирает это поле из исходника. При выпуске старого файла `opf/0.1` CLI требует совпадения его версии с номером релиза.
