# RFC: локальный Git-реестр промптов

Статус: RFC от 2 октября 2026 года. Локальный `opf.yaml`, Git-релизы, каналы, экспорт, Python Jinja-обёртка, загрузка в Python/TypeScript и первый адаптер Langfuse реализованы экспериментально. Точный текущий контракт — в [спецификации реестра](../spec/REGISTRY.md). `opf/0.1` описан [отдельно](../spec/SYNTAX.md).

## Основной сценарий

Автор пишет промпт в Markdown, приложение загружает его по стабильному ID из своего репозитория, а CLI при необходимости публикует **конкретный релиз** во внешний сервис. Локальные файлы и Git остаются источником истины. Python-приложению не нужен сервер реестра; TypeScript-приложение может читать тот же формат и проверять тот же релиз.

Один `opf.yaml` в корне проекта — единственный конфиг, который человек поддерживает для реестра. Промпты остаются отдельными файлами. Git-теги хранят выпущенные версии, а экспортируемые пакеты и квитанции создаются инструментом.

```yaml
schema: opf-registry/1
prompts:
  support.reply:
    source: prompts/support-reply.md
    renderer: opf
    channels:
      production:
        version: 1.2.0
        digest: sha256:...

  legacy.summary:
    renderer: jinja2
    messages:
      - role: system
        file: prompts/legacy/system.md
      - role: user
        file: prompts/legacy/summary.j2
```

Пути, рендерер и каналы описываются здесь. Для существующего проекта с `.md` и `.j2` это обёртка над текущими файлами, без обязательной миграции их содержимого. Реализованный `opf/0.2` оставляет в Markdown сам промпт и объявления входов; версия релиза находится вне файла. `opf/0.1` по-прежнему требует `version` во frontmatter, а CLI проверяет её совпадение с номером релиза.

## Что именно является версией

| Сущность | Где живёт | Что означает |
| --- | --- | --- |
| `id` | `opf.yaml` | Постоянное имя промпта для приложения. |
| Черновик | Рабочее дерево Git | Любые правки до релиза; SemVer на каждую правку не нужен. |
| Релиз `1.2.0` | Аннотированный Git-тег `opf/support.reply/v1.2.0` | Зафиксированный коммит и проверяемый digest всего набора исходников. |
| Канал `production` | Указатель `version` + `digest` в `opf.yaml` | Какой релиз выбирает приложение; перемещение видно в истории Git. |
| Вызов модели | Квитанция рядом с трассировкой | Точный релиз, итоговый рендер и фактические настройки вызова. |

`opf release support.reply --version 1.2.0` требует чистого, уже закоммиченного состояния релевантных файлов, вычисляет `bundle_digest`, создаёт аннотированный тег на текущем коммите и записывает digest в метаданные тега. Тег с тем же именем нельзя использовать повторно. Тег можно передвинуть средствами Git, поэтому `opf verify` сравнивает содержимое тега, ожидаемый digest и выбранный канал; защищённые или подписанные теги могут дополнительно применяться в команде.

`bundle_digest` покрывает основной файл, все статически известные Jinja `include`/`import`/`extends`, относительные пути и параметры рендера, влияющие на результат. Порядок и кодировка канонизируются и закрепляются общими проверочными примерами для Python и TypeScript. Для динамического include нужен явный список допустимых файлов; иначе выпуск завершается ошибкой. `source_digest` из v0.1 хеширует один файл и не заменяет `bundle_digest`.

`opf promote support.reply@1.2.0 --channel production` меняет только указатель в `opf.yaml`; разработчик коммитит изменение обычным способом. Тег релиза указывает на более ранний коммит с исходниками. Релиз не записывает собственный хеш в тот же коммит, чтобы не создавать циклическую зависимость. `opf verify` проверяет указатель, тег и содержимое. Откат — новое перемещение указателя на предыдущий проверенный релиз.

## Локальная загрузка и поставка

Предлагаемый API:

```python
registry = Registry.local("opf.yaml")
prompt = registry.get("support.reply", channel="production")
prepared = prompt.render({"question": question})
```

SDK по умолчанию читает локальный реестр. Указатель `production` разрешается в файлы **релизного Git-коммита**, а не в текущий изменяемый файл по тому же пути; SDK сверяет digest перед рендером. Выбор удалённого источника всегда явный, например `Registry.langfuse(...)`; он не возникает из наличия переменной окружения. В исполняемом пакете может не быть `.git`: `opf export support.reply@1.2.0` создаёт переносимый пакет с исходниками, манифестом и digest из тега. SDK умеет проверить и загрузить этот пакет из wheel, контейнера или другого хранилища. Доставка новой версии в запущенный процесс определяется обычным развёртыванием приложения; отдельная сетевая доставка может добавляться позднее.

## Модель и провайдер

Модель **не является обязательным полем промпта** или `opf.yaml`. Один и тот же промпт может испытываться на разных моделях и публиковаться разным провайдерам. Выбор модели принадлежит приложению или его конфигурации развёртывания; переменная окружения — допустимый способ задать его:

```python
model = os.environ["LLM_MODEL"]
client.responses.create(model=model, input=prepared.messages)
```

Для воспроизведения вызова недостаточно сохранить имя переменной `LLM_MODEL`: квитанция должна содержать **разрешённые значения** провайдера и модели, версию модели, если она доступна, параметры генерации, ID релиза, `bundle_digest` и `render_digest` итоговых сообщений. Значения входов и сам текст сообщений не пишутся в журнал по умолчанию. Смена модели не создаёт новую версию промпта, но меняет запись конкретного вызова и результаты eval. Необязательные `tested_with` или матрица eval могут описывать проверенную совместимость. Адаптер вправе передать настройки модели во внешний сервис, если его API этого требует; локальный формат не получает из-за этого обязательной привязки к провайдеру.

## Публикация наружу

`opf publish support.reply@1.2.0 --to langfuse` экспортирует ровно проверенный релиз. Адаптер до записи показывает, какие роли, шаблонные возможности и метаданные внешний сервис способен сохранить и выполнить. Публикация идемпотентна по локальным `id`, версии и `bundle_digest`; после записи инструмент проверяет доступную удалённую версию и выдаёт квитанцию с внешним ID. Канал во внешнем сервисе перемещается только явной командой. Аналогичный адаптер может быть сделан для MLflow или другого сервиса.

Переносимый пакет остаётся доступен даже если конкретный сервис не умеет выполнять Jinja или хранить все метаданные. В таком случае адаптер сообщает о потере возможностей или публикует уже отрендеренный вариант только по явному запросу. Локальный канал и удалённая метка не синхронизируются скрыто.

## Первый полезный срез

1. Python-обёртка для существующих Markdown/Jinja файлов, строгие ошибки рендера, дерево зависимостей и digest всего набора.
2. Единый `opf.yaml`, локальные `get`, `render`, `release`, `promote`, `verify`, `export` и квитанция вызова.
3. Общие проверочные примеры для заявленного переносимого профиля Python/TypeScript; полный Jinja2 не обещает автоматического совпадения с JavaScript.
4. Один адаптер публикации с проверкой возможностей и удалённого результата.

Критерий успеха: на реальном Python-проекте с `.md` и `.j2` можно установить точный исходник рабочего промпта, откатить канал, воспроизвести рендер и выгрузить тот же релиз наружу без ручного копирования текста.
